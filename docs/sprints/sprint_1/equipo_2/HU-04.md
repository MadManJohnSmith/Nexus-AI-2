## 1. Descripción de la Historia
**Como** coordinador del programa de posgrado,  
**quiero** asociar el Asesor Principal, Coasesor, Secretario y Vocales del comité tutorial a cada estudiante doctorando,  
**para** determinar formalmente quiénes participan en su seguimiento académico, evaluación de avances y registro de acuerdos.

---

## 2. Criterios de Aceptación y Validación (Gherkin)

### CA-04.1: Selección de Usuarios con Roles Compatibles
```gherkin
Escenario: Asignación válida de un usuario con rol ASESOR o COORDINADOR
  Dado que el coordinador desea asignar a 'Dr. Roberto Garcia' (rol ASESOR) al comité
  Cuando envía la petición POST con rol_comite='ASESOR_PRINCIPAL'
  Entonces el sistema valida el rol compatible y crea la asignación exitosamente con HTTP 201 Created.

Escenario: Rechazo de asignación de usuario con rol no compatible
  Dado que el coordinador intenta asignar a 'Daniel Morales' (rol ESTUDIANTE) al comité
  Cuando envía la solicitud de asignación
  Entonces el sistema rechaza la operación con HTTP 400 Bad Request indicando que solo se permiten roles ASESOR o COORDINADOR.
```

### CA-04.2: Vinculación Permanente al Expediente y Unicidad
```gherkin
Escenario: Registro de miembros vinculados al estudiante
  Dado un estudiante con ID 10
  Cuando se consultan sus miembros de comité en GET /api/v2/students/10/committee/
  Entonces se retorna la lista ordenada con sus roles, datos de contacto y fecha de asignación.

Escenario: Prevención de duplicidad de rol para un mismo usuario y estudiante
  Dado que el usuario 2 ya está asignado como 'ASESOR_PRINCIPAL' del estudiante 10
  Cuando se intenta asignar nuevamente el mismo rol al mismo usuario para dicho estudiante
  Entonces el sistema rechaza con HTTP 400 Bad Request por violación de unicidad.
```

### CA-04.3: Habilitación de Participantes para Tutorías
```gherkin
Escenario: Consumo de miembros de comité en tutorías (Sprint 2)
  Dado un estudiante con comité asignado
  Cuando los módulos de tutorías consulten los participantes autorizados
  Entonces el sistema proporciona la lista activa de miembros del comité.
```

## 3. Contratos de API REST v2.0

### Endpoints
- `GET /api/v2/students/<student_id>/committee/`: Lista miembros del comité tutorial.
- `POST /api/v2/students/<student_id>/committee/`: Asigna un nuevo miembro (Solo Coordinador).
- `GET /api/v2/students/<student_id>/committee/<member_id>/`: Detalle de un miembro.
- `DELETE /api/v2/students/<student_id>/committee/<member_id>/`: Remueve un miembro (Solo Coordinador).

### Ejemplo de Payload de Creación (POST):
```json
{
  "user": 2,
  "rol_comite": "ASESOR_PRINCIPAL",
  "fecha_asignacion": "2026-01-15"
}
```

### Ejemplo de Respuesta Exitosa (201 Created):
```json
{
  "committee_member_created_id": 1,
  "mensaje": "Miembro asignado al comité académico correctamente",
  "committee_member": {
    "id": 1,
    "student": 10,
    "user": 2,
    "user_detail": {
      "id": 2,
      "email": "dr.garcia@nexus.edu",
      "full_name": "Dr. Roberto Garcia",
      "role": "ASESOR"
    },
    "rol_comite": "ASESOR_PRINCIPAL",
    "rol_comite_display": "Asesor Principal / Director",
    "fecha_asignacion": "2026-01-15",
    "is_active": true,
    "created_at": "2026-01-15T10:00:00Z",
    "updated_at": "2026-01-15T10:00:00Z"
  }
}
```
