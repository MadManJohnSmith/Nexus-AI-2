## 1. Descripción de la Historia
**Como** administrador o coordinador del sistema,  
**quiero** asignar roles y permisos granulares basados en el modelo de control de acceso por roles y relación con el estudiante (RBAC + Relation-Based Access Control),  
**para** garantizar que cada usuario (Coordinador, Asesor, Estudiante) acceda únicamente a la información y operaciones autorizadas en el expediente doctoral.

---

## 2. Criterios de Aceptación y Validación (Gherkin)

### CA-02.1: Aislamiento del Estudiante
```gherkin
Escenario: Consulta autorizada de expediente por el estudiante
  Dado que un usuario autenticado tiene el rol 'ESTUDIANTE'
  Y su cuenta está vinculada al expediente con ID 10
  Cuando intenta consultar el expediente con ID 10
  Entonces el sistema responde con HTTP 200 OK y entrega los datos.

Escenario: Intento de consulta no autorizada a otro expediente
  Dado que un usuario autenticado tiene el rol 'ESTUDIANTE' asociado al ID 10
  Cuando intenta consultar o acceder al expediente con ID 20 (otro estudiante)
  Entonces el sistema rechaza la petición con HTTP 403 Forbidden.
```

### CA-02.2: Aislamiento del Asesor según Comité Tutorial
```gherkin
Escenario: Asesor asignado consulta expediente de su tutorado
  Dado que un usuario tiene el rol 'ASESOR'
  Y está asignado activamente en el comité tutorial del estudiante 10
  Cuando consulta el expediente, semestres o comités del estudiante 10
  Entonces el sistema permite el acceso con HTTP 200 OK.

Escenario: Asesor no asignado intenta acceder al expediente
  Dado que un usuario tiene el rol 'ASESOR'
  Y NO está asignado en el comité tutorial del estudiante 20
  Cuando intenta consultar el expediente del estudiante 20
  Entonces el sistema rechaza la petición con HTTP 403 Forbidden.
```

### CA-02.3: Supervisión Global del Coordinador
```gherkin
Escenario: Consulta global por el Coordinador
  Dado que un usuario tiene el rol 'COORDINADOR' o es superusuario
  Cuando consulta cualquier expediente, semestre o comité del sistema
  Entonces el sistema autoriza la operación y retorna la información completa con HTTP 200 OK.
```

## 3. Arquitectura e Implementación Técnica

### 3.1 Clases de Permisos DRF (`apps/identity/permissions.py`)
- `RolePermissionBase`: Clase utilitaria que hereda de `rest_framework.permissions.BasePermission`, validando autenticación y membresía en `allowed_roles` o `is_superuser`.
- `IsCoordinator`: Permiso para vistas administrativas y de asignación (rol `COORDINADOR`).
- `IsAdvisor`: Permiso para vistas exclusivas de asesoría (rol `ASESOR`).
- `IsStudent`: Permiso para vistas exclusivas de doctorandos (rol `ESTUDIANTE`).
- `IsAssignedAdvisorOrStudent`: Permiso contextual a nivel de objeto (`has_object_permission`) que valida:
  1. Si el usuario es Coordinador / Superusuario -> Acceso global concedido.
  2. Si el objeto es un `Student` -> Valida que `student.user == request.user` o que `student.committee_members.filter(user=request.user, is_active=True).exists()`.
  3. Si el objeto contiene relación `student` (Semestre, Tutoría, etc.) -> Valida contra el estudiante asociado.
