## 1. Descripción de la Historia
**Como** asesor o miembro del comité tutorial,  
**quiero** formalizar acuerdos y compromisos académicos vinculados o derivados directamente de las sesiones de tutoría o del expediente del estudiante,  
**para** establecer compromisos claros, accionables y trazables dentro del programa doctoral.

---

## 2. Criterios de Aceptación y Validación (Gherkin)

### CA-11.1: Registro de Acuerdo Vinculado a Sesión de Tutoría
```gherkin
Escenario: Creación exitosa de acuerdo derivado de una tutoría
  Dado que un asesor autenticado se encuentra en el expediente de su tutorado
  Y existe una sesión de tutoría registrada con ID 101
  Cuando envía una solicitud POST a '/api/v2/agreements/' con descripción, sesión 101, estudiante y fecha límite
  Entonces el sistema responde con HTTP 201 Created
  Y el cuerpo de respuesta contiene "agreement_created_id", "mensaje": "Acuerdo registrado exitosamente" y el objeto completo.
```

### CA-11.2: Registro de Acuerdo Directo sin Sesión de Tutoría
```gherkin
Escenario: Creación de acuerdo directo en el expediente del estudiante
  Dado que un asesor o coordinador desea registrar un compromiso extraordinario
  Cuando envía una solicitud POST a '/api/v2/agreements/' con session=null
  Entonces el sistema crea el acuerdo correctamente asociado al estudiante con HTTP 201 Created.
```

### CA-11.3: Validación de Integridad de Sesión y Estudiante
```gherkin
Escenario: Rechazo de sesión de tutoría que no corresponde al estudiante
  Dado que se intenta registrar un acuerdo indicando student=1 y session=5 (perteneciente a student=2)
  Cuando se envía el payload al endpoint
  Entonces el backend responde con HTTP 400 Bad Request indicando que la sesión no pertenece al estudiante.
```

## 3. Arquitectura e Implementación Técnica

### 3.1 Modelo de Datos (`backend/apps/agreements/models.py`)
- Modelo `Agreement`:
  - `session`: `ForeignKey` a `tutoring.TutoringSession` (`null=True`, `blank=True`, `on_delete=models.SET_NULL`).
  - `student`: `ForeignKey` a `students.Student` (`on_delete=models.CASCADE`, `db_index=True`).
  - `descripcion`: `TextField` con la descripción del compromiso acordado.
  - `responsable`: `ForeignKey` al modelo de usuario (`CustomUser`).
  - `fecha_limite`: `DateField` indexado.
  - `estado`: `CharField` con choices (`PENDIENTE`, `EN_PROCESO`, `CONCLUIDO`, `VENCIDO`), default `PENDIENTE`.
  - `fecha_conclusion`: `DateField` (`null=True`, `blank=True`).
  - `created_by`: `ForeignKey` al usuario creador.
  - `created_at` / `updated_at`: Marcas temporales automáticas.

### 3.2 Serializers y Endpoints (`backend/apps/agreements/serializers.py` & `views.py`)
- `AgreementCreateSerializer`: Valida pertenencia de la sesión, compatibilidad del responsable y asigna automáticamente `created_by`.
- `AgreementSerializer`: Enriquecido con campos display (`responsable_nombre`, `student_nombre`, `is_vencido`, `audit_logs`).
- `AgreementViewSet`: Registrado bajo `/api/v2/agreements/`.
