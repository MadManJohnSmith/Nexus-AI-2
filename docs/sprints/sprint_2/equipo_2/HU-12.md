## 1. Descripción de la Historia
**Como** asesor o coordinador académico,  
**quiero** asignar explícitamente un responsable (doctorando, asesor principal, coasesor o miembro de comité) y una fecha límite compromiso para cada acuerdo,  
**para** delimitar responsabilidades claras y habilitar el control y semáforo automático de vencimientos.

---

## 2. Criterios de Aceptación y Validación (Gherkin)

### CA-12.1: Asignación Válida de Responsable
```gherkin
Escenario: Asignación de doctorando o miembro de comité como responsable
  Dado que se registra un acuerdo para el estudiante "Juan Pérez"
  Cuando se selecciona como responsable al propio estudiante o a su asesor de comité
  Entonces el sistema valida la compatibilidad de roles y almacena la asignación con HTTP 201 Created.
```

### CA-12.2: Validación de Fecha Límite y Detección de Vencimiento
```gherkin
Escenario: Detección automática de acuerdo vencido
  Dado un acuerdo existente con fecha límite en el pasado respecto a la fecha del sistema
  Y cuyo estado actual es diferente a 'CONCLUIDO'
  Cuando se consulta el acuerdo o se ejecuta el ciclo de evaluación
  Entonces el sistema transiciona automáticamente el estado a 'VENCIDO' y marca is_vencido = true.
```

---

## 3. Arquitectura e Implementación Técnica

### 3.1 Lógica de Dominio (`backend/apps/agreements/models.py`)
- Método `check_and_update_overdue(save=True)`: Actualiza el estado a `VENCIDO` si `fecha_limite < timezone.now().date()` y `estado != 'CONCLUIDO'`.
- Propiedad `@property def is_vencido`: Determina si el compromiso expiró sin ser concluido.
- `AgreementQuerySet.update_overdue_statuses()`: Ejecuta actualización por lotes en consultas DRF para consistencia a nivel de base de datos.

### 3.2 Frontend Drawer (`frontend/src/app/features/agreements/agreement-drawer/`)
- Selector reactivo de responsables vinculados al comité tutorial y al estudiante.
- Datepicker con validaciones obligatorias de fecha límite.
- Semáforo visual Pill Badge reflejando el estado de compromiso.
